ОРГАНІЗАЦІЯ КОМАНДНОЇ РОБОТИ З ДИСЦИПЛІНИ
«СЕРВЕРНЕ ВЕБПРОГРАМУВАННЯ»

Версія 2 (вересень 2026). Попередня версія: organizatsiya_server_web_programming_v1_original.txt

Основні зміни порівняно з версією 1:
- задачі нарізані вертикально (по сутностях), а не шарами — студенти працюють паралельно і не чекають одне одного;
- кожна команда стартує з готового шаблону проєкту (скелет рішення, PostgreSQL у Docker, тести, CI);
- робота йде через гілку dev за моделлю Streetcode: PR -> рев'ю одногрупника -> рев'ю викладача -> захист -> merge;
- CI (GitHub Actions) автоматично перевіряє збірку і тести кожного PR;
- переглянуто шкалу балів: XL — лише складна бізнес-логіка, а не конфігурація;
- Docker з'являється на початку (PostgreSQL з ЛР3), а не лише на ЛР9;
- додано явний поріг балів для оцінки та правило для EF Core міграцій.


1. Загальна модель організації

До 30 студентів — 5 команд по 5–7 осіб (максимум 7).

30 студентів
   |
   +-- Team 1 — University Management API
   +-- Team 2 — Hotel Booking API
   +-- Team 3 — Library Management API
   +-- Team 4 — Clinic Appointment API
   +-- Team 5 — Online Store / Warehouse API

Технологічні вимоги однакові для всіх команд, предметні області різні.

Спільний стек:

ASP.NET Core 10 (Web API, контролери)
REST API + OpenAPI
Entity Framework Core 10
PostgreSQL 17
Authentication (JWT) / Authorization (ролі, політики)
Files (завантаження, експорт/імпорт)
SignalR
Testing (xUnit, WebApplicationFactory, Testcontainers)
Docker / Docker Compose
GitHub Actions (CI)

Окрема GitHub Organization викладача (не пов'язана з іншими організаціями):

PNU-Server-Web-2026

Репозиторії:

team-04-clinic

Репозиторії публічні: на безкоштовному плані організації захист гілок

3. Шаблон проєкту

Кожен командний репозиторій створюється з готового скелета:

- рішення .sln: src/<Project>.Api + tests/<Project>.Api.Tests;
- Directory.Build.props (Nullable, TreatWarningsAsErrors) і
  Directory.Packages.props (єдині версії пакетів для всієї команди);
- DbContext із підключенням до PostgreSQL (без сутностей);
- docker-compose.yml з PostgreSQL;
- тестовий проєкт із WebApplicationFactory і першим тестом;
- CI: збірка + тести на кожен PR;
- шаблони Issue і Pull Request, CODEOWNERS;
- README.md і CONTRIBUTING.md з правилами роботи.

Структура коду — vertical slice: кожна функціональність живе у своїй папці
Features/<Назва>/ (контролер, DTO, сервіс, реєстрація залежностей).
Так студенти рідше редагують одні й ті самі файли.

Команді не потрібно витрачати перший тиждень на «хто створить solution» —
з першого заняття всі 6 студентів можуть брати задачі.


4. Гілки та Pull Request (модель Streetcode)

Гілки:

main  — стабільна версія; оновлюється викладачем наприкінці кожного спринту (ЛР)
dev   — гілка інтеграції, default branch; усі PR ідуть сюди

Пряма робота в dev і main заборонена (branch protection).

Назви гілок:

feat/<issue>/<опис>     — нова функціональність
fix/<issue>/<опис>      — виправлення
test/<issue>/<опис>     — тести
chore/<issue>/<опис>    — інфраструктура, Docker, CI
docs/<issue>/<опис>     — документація

Приклад: задача #34 «Пошук вільних номерів» -> гілка feat/34/free-rooms-search

Коміти — Conventional Commits: feat:, fix:, test:, refactor:, chore:, docs:.

Умови merge у dev (налаштовуються автоматично):
- зелений CI (збірка + тести);
- 2 approve: одногрупник + викладач (CODEOWNERS);
- усі коментарі рев'ю resolved;
- squash merge (одна задача = один коміт у dev, авторство збережено).

Робочий процес:

Issue
  |
гілка від dev
  |
commits
  |
Pull Request у dev  (Closes #<номер>)
  |
рев'ю одногрупника
  |
рев'ю викладача
  |
короткий усний захист
  |
merge у dev -> Issue закривається автоматично -> DONE


5. Структура задачі (Issue)

Кожна задача оформлюється як GitHub Issue у стилі user story:

Заголовок: [Область] Коротко, що зробити
Опис: «Як <роль>, я хочу <...>, щоб <...>»
Acceptance Criteria — перевірюваний чекліст
Технічні вимоги — що саме використати
Залежить від — номери задач, які мають бути виконані раніше
Розмір / Points / Категорія / Спринт

Приклад:

[Books] Пошук книг за назвою та автором

Як читач, я хочу шукати книги за частиною назви або прізвища автора,
щоб швидко знайти потрібну книгу.

Acceptance Criteria:
- [ ] GET /api/books/search?query=... повертає 200 OK і масив книг;
- [ ] пошук без урахування регістру, за частиною слова;
- [ ] якщо збігів немає — порожній масив, а не 404;
- [ ] порожній query -> 400 Bad Request (ProblemDetails);
- [ ] є інтеграційний тест на кожен пункт вище.

Технічні вимоги: EF Core, EF.Functions.ILike, асинхронні методи, AsNoTracking.
Розмір: M — 2 points. Категорія: api.

Задача без Acceptance Criteria не переводиться в READY.


6. Дошка задач (GitHub Project)

Статуси:

Backlog      — задача чекає на залежності або на свій спринт
Ready        — можна брати
In Progress  — виконується
Review       — відкрито PR, чекає рев'ю/захисту
Done         — перевірено, захищено, злито в dev

Поля дошки: Status, Points (число), Size (S/M/L/XL), Milestone (спринт).

Задача переходить із BACKLOG у READY, коли закриті всі її залежності
і настав її спринт (синхронізацію виконує викладач скриптом).


7. Обмеження на активні задачі

Один студент одночасно має:
- максимум 1 задачу в IN PROGRESS;
- максимум 1 задачу в REVIEW.

Нову задачу можна брати після того, як попередню передано в REVIEW.

Якщо протягом 7 днів у задачі немає коміту або PR — вона повертається в READY,
студент знімається з призначення.

За одне заняття студент захищає не більше 3 задач. Відкладати все на кінець
семестру не вийде: захистити 10 задач в останній тиждень фізично неможливо.


8. Task Points

S  — проста задача        — 1 point
M  — середня задача       — 2 points
L  — складна задача       — 3 points
XL — велика бізнес-задача — 5 points

Орієнтири:

Swagger UI / health checks / конфігурація          — 1
Сутність + EF-конфігурація + міграція              — 1
CRUD-контракт сутності (DTO + контролер + сервіс)  — 2
EF-реалізація сервісу сутності                     — 2
Зв'язок 1:N з endpoint-ами                         — 2
Upload файлу з валідацією                          — 2
Зв'язок M:N з додатковими даними                   — 3
JWT login / refresh tokens / resource-based authz  — 3
SignalR hub з автентифікацією                      — 3
Docker Compose: API + PostgreSQL + міграції        — 3
Складне бізнес-правило (перетин дат, конкурентність, розрахунки) — 5

Бал враховується лише за задачу в статусі DONE.


9. Оцінювання

70 % — індивідуальні Task Points
20 % — стан командного проєкту
10 % — підсумковий індивідуальний захист

Індивідуальна частина:
- 22 бали і більше = 70 з 70;
- менше — пропорційно: оцінка = 70 * бали / 22;
- для максимуму потрібні задачі щонайменше з 5 різних категорій;
  якщо категорій менше 5 — індивідуальна частина не більше 56 з 70.

Приклад: 2 + 1 + 3 + 2 + 3 + 5 + 2 + 3 = 21 бал з 6 категорій -> 70 * 21/22 = 66,8.

Командна частина (20):
- dev збирається, усі тести зелені                    — 5
- docker compose up піднімає робочу систему            — 5
- наскрізний демо-сценарій предметної області працює  — 5
- якість: README, OpenAPI, відсутність «мертвого» коду — 5

Кожна команда має в backlog приблизно 87 задач на ~170 балів — з запасом
(7 студентів × 22 = 154), щоб кожен студент мав з чого набрати поріг.
На старті семестру в READY одразу 11 задач — роботи вистачає всім.


10. Категорії задач (labels)

http          — HTTP, middleware, конфігурація, помилки, логування
api           — REST endpoints, DTO, валідація, пошук, пагінація
ef-core       — сутності, зв'язки, запити, міграції
database      — обмеження, індекси, seed, транзакції, конкурентність
architecture  — сервіси, DI, бізнес-правила, фонові задачі, кешування
security      — автентифікація, авторизація, секрети
testing       — unit та інтеграційні тести
docker        — Docker, Compose, CI/CD
signalr       — real-time сповіщення
files         — завантаження/віддача файлів, імпорт/експорт

Додаткові labels: size: S / M / L / XL, blocked, bug.


11. Спринти = лабораторні роботи

Кожна ЛР — це milestone (спринт) у GitHub.

S1 / ЛР1 — Проєкт та HTTP API: OpenAPI, health checks, конфігурація, ERD
S2 / ЛР2 — REST endpoints: DTO, контролери, валідація, пагінація (сервіси in-memory)
S3 / ЛР3 — EF Core і PostgreSQL: сутності, міграції, EF-реалізація сервісів
S4 / ЛР4 — Складніша модель даних: 1:N, M:N, soft delete, аудит, конкурентність
S5 / ЛР5 — Архітектура: бізнес-правила, доменні помилки, DI, фонові сервіси, кеш
S6 / ЛР6 — Middleware, обробка помилок, логування, rate limiting
S7 / ЛР7 — Authentication / Authorization
S8 / ЛР8 — SignalR, файли, тести на реальній БД
S9 / ЛР9 — Docker, CI/CD, фінальний демо-сценарій, захист

Підхід «спочатку контракт»: у S2 команда описує REST API і реалізує сервіси
в пам'яті; у S3 in-memory реалізації замінюються на EF Core через DI.
HTTP-тести, написані в S2, мають проходити і після заміни — це наочно показує,
навіщо потрібні інтерфейси та Dependency Injection.

На ЛР викладач:
- пояснює новий етап;
- консультує;
- перевіряє стан проєкту;
- приймає короткі захисти задач;
- наприкінці спринту зливає dev у main.


12. Залежності між задачами

Залежності мінімальні й лише справжні. Приклад для Hotel Booking:

#Hotels-контракт (S2) ----> #Hotels EF-реалізація (S3)
#Hotel entity (S3)   ---/
#Room entity (S3) --> #Hotel-Room 1:N (S4) --> #Пошук вільних номерів (S4)
#Реєстрація (S7) --> #JWT login (S7) --> #Refresh tokens (S7)

Задачі різних сутностей між собою не залежать — 6 студентів можуть
паралельно працювати над Hotels, Rooms, Guests, Bookings, Reviews.


13. Правило для EF Core міграцій

Міграція — частина PR задачі, що змінює модель (окремої задачі «додати
міграції» немає). Якщо поки PR був відкритий, у dev з'явилися нові міграції:
rebase на dev, видалити свою міграцію, згенерувати її заново.
Інакше ModelSnapshot конфліктуватиме.


14. Командні ролі

1 — coordinator (стежить за дошкою, READY/BACKLOG, дедлайнами)
2 — database
3 — API
4 — security
5 — testing
6 — deployment

Ролі змінюються 2–3 рази за семестр. Роль не обмежує вибір задач
і не впливає на оцінку напряму.


15. Перевірка задач

Кожен PR проходить три рівні:

1. CI — автоматично: збірка без попереджень, усі тести зелені.
2. Рев'ю одногрупника — обов'язковий approve іншого студента команди
   (вчить читати чужий код; якісне рев'ю — теж навичка).
3. Рев'ю викладача — перевірка Acceptance Criteria, якості коду, тестів.
   Викладач використовує AI-асистента (Claude) для попереднього аналізу PR:
   відповідність Acceptance Criteria, типові помилки, питання до захисту.
   Остаточне рішення приймає викладач.

Використання AI студентами не заборонене. Задача зараховується лише після
короткого усного захисту (2–3 хвилини), на якому студент пояснює свій код.

Приклади питань:
- Чому тут FirstOrDefaultAsync, а не First?
- Що буде, якщо прибрати [Authorize]?
- Де саме EF Core виконує SQL-запит? Скільки запитів буде тут?
- Чому цей сервіс зареєстрований як Scoped?
- Що станеться, якщо викликати endpoint з неправильними даними?
- Що буде, якщо два користувачі одночасно забронюють той самий номер?

Якщо студент не може пояснити свій код — задача повертається в IN PROGRESS.


16. Самостійна робота

60 годин самостійної роботи — виконання задач з backlog між заняттями.

лекція -> пояснення технології
лабораторна -> старт спринту, консультація, захисти
самостійна робота -> виконання Issues
Pull Request -> рев'ю
захист -> зарахування Task Points


17. Робочий цикл студента

1. Відкрити дошку команди, вибрати задачу в READY.
2. Призначити Issue на себе, перевести в IN PROGRESS.
3. git checkout dev && git pull; створити гілку feat/<issue>/<опис>.
4. Реалізувати, написати тести, зробити коміти.
5. Відкрити PR у dev, у описі — Closes #<issue>, заповнити чекліст.
6. Перевести задачу в REVIEW, попросити одногрупника про рев'ю.
7. Виправити зауваження одногрупника і викладача.
8. Захистити задачу на занятті.
9. Після approve викладача — squash merge; Issue автоматично закривається -> DONE.
10. Бали зараховуються.


18. Основний принцип

Дисципліна організована не як набір однакових індивідуальних лабораторних,
а як робота кількох невеликих команд над реальними серверними проєктами.

Кожна команда створює один серверний застосунок.
Кожен студент має власний набір задач і власні бали.

Індивідуальний внесок визначається за:
- закритими Issues та їх Points;
- комітами і Pull Request;
- якістю рев'ю, які студент робив одногрупникам;
- коротким усним захистом.
